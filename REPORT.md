## 2. Підхід Code-First для документування REST API

На відміну від підходу **Design-First** (який застосовувався у практичній роботі № 4 шляхом ручного складання файлу `openapi.yaml`), підхід **Code-First** дозволяє підтримувати єдине джерело правди безпосередньо у вихідному коді бекенда.

### 2.1. Конфігурація плагіна компілятора NestJS CLI
У файлі `nest-cli.json` активовано AST-плагін `@nestjs/swagger`:
```json
{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "deleteOutDir": true,
    "plugins": [
      {
        "name": "@nestjs/swagger",
        "options": {
          "classValidatorShim": true,
          "introspectComments": true,
          "dtoFileNameSuffix": [".dto.ts", ".entity.ts"]
        }
      }
    ]
  }
}
```
Параметр `introspectComments: true` автоматично трансформує стандартні коментарі JSDoc у поля `description` та `@example` OpenAPI-схеми, а `classValidatorShim: true` трансформує валідатори `class-validator` (`@Min`, `@Max`, `@IsEnum`, тощо) у відповідні обмеження схеми (`minimum`, `maximum`, `enum`).

### 2.2. Генерація специфікації та Swagger UI
У `src/swagger.ts` реалізовано фабрику `buildOpenApiDocument`:
- Заголовок, детальний опис та версія динамічно витягуються з `package.json` через `appInfoFactory()`.
- Сконфігуровано сервер API: `http://localhost:3000/api/v1` з опцією `ignoreGlobalPrefix: true`.
- Додано глобальну схему безпеки Bearer-автентифікації (`addBearerAuth`) та теги категорій маршрутів (`auth`, `tickets`, `comments`, `users`).
- Підключено Swagger UI за адресою `/api/docs` зі збереженням токена авторизації (`persistAuthorization: true`) та відкритий ендпоінт специфікації у форматі JSON за адресою `/api/docs-json`.
- Створено скрипт `src/openapi.export.ts`, який ініціалізує контекст додатку NestJS без запуску мережевого HTTP-лістенера та експортує актуальну специфікацію у файл `openapi.json`.

## 3. Складені мета-декоратори документації

Для скорочення бойлерплейту та суворого дотримання стандарту API розроблено набір складених декораторів (`src/common/api/api-docs.decorators.ts`) з використанням утиліти NestJS `applyDecorators`:

| Декоратор | Призначення | Згенерована структура OpenAPI |
|---|---|---|
| `ApiProblemResponses(...codes)` | Опис типових відповідей про помилки (400, 401, 403, 404, 409, 422, 500) | Додає схеми відповідей із медіатипом `application/problem+json` та посиланням на схему `ProblemDetailsEntity` ($ref) |
| `ApiPageResponse(Model, description)` | Опис сторінки колекції ресурсів | Описує відповідь `200 OK` для пагінованого списку `{ items: [Model], page, pageSize, total }` із валідними прикладами |
| `ApiCreatedWithLocation(Model, description)` | Опис створення ресурсу | Описує відповідь `201 Created` із сутністю `Model` та обов'язковим заголовком `Location` формату `uri-reference` |

## 4. Перевірка стилю API лінтером Spectral

Для гарантії того, що автоматично згенерований контракт відповідає всім корпоративним правилам проектування REST API, специфікацію `openapi.json` перевірено лінтером **Spectral** (`npm run lint:api`) з набором правил `api-lint/.spectral.yaml`:
- **problem-details-errors:** усі клієнтські помилки 4xx та серверні помилки 5xx обов'язково мають тип `application/problem+json`;
- **post-creates-resource:** операції створення через `POST` повертають статус `201 Created` та заголовок `Location`;
- **paged-collections:** усі маршрути повернення колекцій підтримують пагінацію зі стандартними параметрами `page`, `pageSize` та повертають об'єкт із полем `total`;
- **no-client-error-schema-in-2xx:** коди успіху не повинні посилатися на моделі винятків.

Результат виконання лінтера: **0 помилок** (повна відповідність контракту вимогам ПР4).

## 7. Відповіді на контрольні запитання

### 1. У чому полягають переваги та недоліки підходів Code-First та Design-First при проєктуванні REST API?
**Відповідь:** 
- **Design-First (ПР4):** специфікація OpenAPI пишеться до написання коду. Переваги: узгодження контракту між фронтенд- і бекенд-командами до початку розробки, можливість негайного створення мок-серверів та клієнтських SDK. Недоліки: ризик розходження між документацією та реальною реалізацією («дрифт документації»), якщо розробники забувають оновлювати YAML-файл при зміні бекенд-коду.
- **Code-First (ПР8):** специфікація генерується автоматично з коду, декораторів та типів бекенда. Переваги: документація завжди синхронізована з кодом, відсутність дублювання опису моделей даних, мінімальні витрати часу на підтримку. Недоліки: неможливість поділитися API-контрактом до завершення написання перших версій контролерів та DTO.

### 2. Як працює плагін компілятора `@nestjs/swagger` і чому його використання є ефективнішим за ручне декорування?
**Відповідь:** Плагін компілятора перехоплює процес транспіляції TypeScript у JavaScript на етапі абстрактного синтаксичного дерева (AST). Він автоматично аналізує класи `*.dto.ts` та `*.entity.ts`, витягує типи властивостей, опціональність (`?`), коментарі JSDoc та правила бібліотеки `class-validator`. Замість необхідності вручну писати `@ApiProperty({ type: String, required: false, description: "..." })` над кожним полем кожної моделі, плагін додає ці метадані самостійно під час компіляції. Це скорочує обсяг коду на 40–60% і запобігає людським помилкам.

### 3. Для чого призначена функція `applyDecorators` у NestJS та як вона допомагає створювати власні мета-декоратори документації?
**Відповідь:** `applyDecorators` дозволяє об'єднувати декілька декораторів у єдиний багаторазовий складений декоратор. Наприклад, опис відповіді пагінації вимагає виклику `ApiExtraModels(model)`, опису коду `200`, визначення схеми об'єкта, полів `items`, `page`, `pageSize`, `total` та посилань `$ref`. Завдяки `applyDecorators` увесь цей складний блок згортається в один лаконічний виклик `@ApiPageResponse(TicketEntity, 'Сторінка заявок')`, що усуває дублювання коду в контролерах.

### 4. Чому важливо розділяти доменні моделі сутностей (`ticket.model.ts`) та моделі документації відповідей (`ticket.entity.ts`)?
**Відповідь:** Доменні моделі та внутрішні представлення даних сервісу часто містять службові поля, приватні прапорці або складні внутрішні типи (наприклад, методи, обчислювані гетери чи парольні хеші). Класи `*.entity.ts` описують публічний контракт, який клієнт реально отримує через мережу. Окремі класи сутностей дозволяють розміщувати JSDoc-коментарі та OpenAPI-декоратори, орієнтовані на зовнішніх розробників, не засмічуючи доменну логіку бекенда.

### 5. Як за допомогою лінтера Spectral забезпечити автоматичний контроль якості згенерованого API-контракту в CI/CD?
**Відповідь:** Spectral приймає згенерований файл `openapi.json` та зіставляє його з набором формальних правил (`.spectral.yaml`). Кожне правило перевіряє певний аспект архітектури: наявність опису заголовків `Location` при `201`, заборону 200-відповідей без схем, використання обов'язкового медіатипу `application/problem+json` для помилок, обов'язкову пагінацію колекцій. Якщо лінтер виявляє помилку із рівнем суворості `error`, команда завершується з ненульовим кодом повернення (`--fail-severity=error`), що автоматично блокує проходження CI/CD пайплайну і запобігає деплою некоректного API.

### 6. Навіщо у конфігурації Swagger застосовується опція `operationIdFactory`?
**Відповідь:** За замовчуванням NestJS генерує довгі та незручні ідентифікатори операцій, що поєднують назву контролера та методу (наприклад, `TicketsController_createTicket`). `operationIdFactory: (_controllerKey, methodKey) => methodKey` змушує генератор використовувати лаконічну назву самого методу (`createTicket`, `listTickets`). Це має вирішальне значення під час кодогенерації клієнтських бібліотек (наприклад, через `openapi-typescript` або `openapi-generator`), оскільки імена методів у згенерованому SDK будуть читабельними, передбачуваними та повністю відповідатимуть дизайну API.

### 7. Чому службовий `HealthController` виключається з публічної документації за допомогою `@ApiExcludeController()`?
**Відповідь:** Маршрут `GET /health` є внутрішнім інфраструктурним ендпоінтом для систем оркестрації контейнерів (Kubernetes liveness/readiness probes, Docker healthcheck, балансувальників навантаження). Він не належить до бізнес-домену системи технічної підтримки коледжу та не використовується кінцевими клієнтами API. Його виключення запобігає перевантаженню публічної документації технічними деталями серверної інфраструктури.

### 8. Які переваги надає автоматична генерація TypeScript-типізованого клієнта на основі `openapi.json`?
**Відповідь:** 
1. **Повна синхронізація типів (End-to-End Type Safety):** фронтенд-розробники отримують 100% відповідність TypeScript-інтерфейсів бекенду.
2. **Автодоповнення в IDE:** середовище розробки підказує точні назви полів запиту та відповіді, можливі enum-значення фільтрів та параметри сортування.
3. **Виявлення несумісних змін (Breaking Changes) на етапі компіляції:** якщо на бекенді змінюється або перейменовується поле в DTO, генерація клієнта негайно спричинить помилку компіляції TypeScript на фронтенді ще до запуску застосунку в продакшн.
